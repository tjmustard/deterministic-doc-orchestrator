## Problem Statement

DDO v0.0.2 shipped the full adversarial loop (Red Team → Interview → Refine), but the patch DSL inside `ddo-refine` only supports `set` on leaf-scalar fields. This means any Red Team finding that requires a structural document change — adding a new evidence entry, removing a stale claim, inserting a new section — cannot be resolved through the pipeline. This session captured requirements for v0.0.3 to close that gap.

## Key Decisions & Rationale

| Decision | Alternatives Considered | Reason Chosen |
|---|---|---|
| v0.0.3 = structural patches | review_history cap/prune; new doc type; composite ddo-run macro | Structural patches are the only gap that blocks real document repair workflows; the others are convenience features or explicitly tech-debt |
| Operations: append + delete + insert | append + delete only (recommended as simpler); include type-change set | User wanted insert — it unlocks prepend and mid-list insertion. Type-change remains too high blast radius |
| Delete safety: refuse with dangling-ref error | Cascade delete refs; warn and proceed | Fail-closed mirrors existing no-auto-vivify invariant; never silently corrupt document integrity |
| Insert position: separate `at: N` field | Encode in path as `[N]` (overloads existing index semantics) | Separate field keeps path grammar unambiguous — path always means "navigate to" not "insert before" |
| No extra HITL gate for structural ops | Require `confirm delete` before committing any delete patch | Existing Before/After diff gate is sufficient and visible; extra step adds friction for no safety gain |
| Existing Before/After diff covers AI-generated values | Candidate Artifact protocol for patch values | Patch values are document content (not test fixtures); the diff gate IS the human verification step |
| Integration fixture: parametrized alongside existing | New standalone test; unit tests only | Parametrized case adds structural coverage while preserving the existing regression baseline |

## Patterns & Lessons

- **Lead-with-recommendation interview style:** The architect skill's "Recommended: [answer]. [Question]?" pattern lets the user move very fast when they agree with the default — most questions in this session were accepted as-is. Only the operation selection (user added `insert`) and the decision to exclude type-change set required real deliberation.

- **Codebase-first before any question:** The Explore agent read the full architecture graph and all resolved Red Team trade-offs before the first question was asked. This meant the session could directly reference RT #8 from the v0.0.2 log as the source of the v0.0.3 deferral — no re-derivation needed in the interview.

- **Plan mode as interview container:** The architect interview ran entirely within plan mode (read-only), building the Draft PRD content in the plan file. The plan file served as the "scratchpad" PRD; ExitPlanMode triggered the actual write to `spec/active/`. This separation cleanly enforces that no draft is written until the interview is complete.

- **`insert` adds a new field type to the patch schema:** The `at: N` field on insert patches is the first patch field that only applies to one op type. This pattern (op-specific optional fields) should be documented in the patch DSL reference section of any future schema guide.

- **Dangling-ref guard scope-creep risk:** The guard is scoped to `evidence_bank` deletions only in v0.0.3 (the only cross-reference constraint in the current schema). If new schemas add their own reference constraints, the guard will need to be generalized. This is flagged explicitly in the Risks table.
