## Key Decisions & Rationale

| Decision | Alternatives Considered | Reason Chosen |
|---|---|---|
| v0.0.4 uses Markdown attack vector tables, not YAML schema | Full YAML persona schema with `ddo.review` category-presence validation | YAML approach required backward compat migration for existing personas and `red_team_report_vN.yaml` files, two codepaths in `ddo.review`, schema surgery — cost too high for the consistency gain |
| Category validation is cognitive (AI follows instructions) not mechanical | Validation gate scan for category presence | Same tradeoff accepted for style injection; system value is reproducible *structure*, not AI output policing |
| Style profiles are Markdown files in `ddo/styles/` | Inline YAML fields in `document_data.yaml`; global `writing_style.yaml` | Mirrors persona pattern exactly; zero new infrastructure; human-editable prose is more expressive than structured fields |
| No forbidden-token scan in validation gate | Extend `ddo.validation` with a forbidden-string scan | Scan requires machine-parseable rules; Markdown prose is not parseable; cognitive injection achieves the same goal at zero infra cost |
| Attack vector IDs are per-persona (AV-01 per persona) | Globally unique IDs across all personas | Simpler; no cross-persona coordination overhead; global uniqueness solves a problem not yet demonstrated |
| Tutorial 2 introduces four document types | Single document type for Tutorial 2 | Real-world coverage (casual blog → business report) better demonstrates DDO's generality |
| `ddo-create-persona` belongs in v0.0.4 | Defer to a later version | Natural pairing: standardize the format, then provide tooling to author new ones correctly |
| Bug fix in `refine.py:276` removed both `is not None` guards | Keep the guard, handle None explicitly | The MiniPRD contract is unambiguous: "set is leaf-scalar-only, no type change" with no exceptions; NoneType and str are distinct types |

## Patterns & Lessons

- **The audit catches what the spec misses.** The `null→scalar` type-change bug passed all 40 tests before the audit (test coverage didn't include that boundary case). Parallel subagent contract verification found it by reading the MiniPRD contract literally against the code, not by running tests.

- **Name things what they are, not what they aspire to.** The v0.0.4 feature was called "DSL" in the brief. Calling it a DSL implied grammar, parsing, and evaluation machinery — and attracted a design that would have required schema migration, two codepaths, and `ddo.review` surgery. Renaming to "Structured Persona Nomenclature" collapsed the design to a Markdown table + skill update.

- **The persona pattern is composable.** Both v0.0.4 (attack vector tables in persona Markdown) and v0.0.5 (style profile Markdown files) arrived at the same implementation shape: a `.md` file in a `ddo/` subdirectory, injected cognitively into the relevant skill. This pattern requires zero Python module changes and is user-editable. When in doubt, prefer this pattern before reaching for structured validation.

- **Challenge the brief before designing.** The user's initial brief described a YAML persona schema with category-presence validation in `ddo.review`. Two rounds of questioning (backward compat cost, style/persona coupling) revealed the actual goal was nomenclature consistency, not machine validation. The correct design was much simpler than the brief implied.
