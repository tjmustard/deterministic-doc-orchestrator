## Problem Statement

Two tutorials existed in `tutorials/` — one frozen at v0.0.1 and one at v0.0.2 — while the codebase had advanced to v0.0.3. The v0.0.3 release introduced new patch ops (`append`, `delete`, `insert`), deprecated two existing ops (`append_evidence`, `append_review_log`), added `DanglingRefError`, enforced an NC-13 path whitelist, and added per-op field validation in `validate_interview_log()`. Neither tutorial reflected these changes. The session goal was to audit both tutorials and produce structured, constraint-aware fix prompts (audit files) that a subsequent fix agent could act on.

## Approach & Methodology

This session used a **plan-first, sequential-audit** approach. The session opened in plan mode, which required gathering full context before any action. Three Explore/Plan subagents were launched in parallel to understand tutorial content, the audit skill's behavior, and changelog/codebase changes simultaneously. A Plan agent then synthesized findings into an execution plan. The plan was approved, and `/hyper-tutorial-audit` was invoked sequentially on each tutorial — Audit 1 first, Audit 2 second — because the skill is interactive (HITL gates require user input between steps). No HACF architecture or implementation phases were invoked; this session was purely an audit/documentation workflow.

## Patterns & Lessons

- **Pre-seeding HITL gates with research pays off.** The three parallel subagents (Explore × 2 + Plan) took ~2 minutes total and meant every Gate question could be answered in seconds with high confidence. Skipping the plan step would have risked missing issues during the interactive interview.

- **The audit skill's "pre-fill from context" constraint is real.** Gate 3 was correctly skipped for Audit 2 because environment data was already in context. Reading the skill's constraints before running it prevents redundant questions.

- **Tutorial scope discipline matters.** Tutorial 1 covers v0.0.1 rendering; its fix should not scope-creep into adversarial loop content. Tutorial 2 covers the v0.0.2 loop; v0.0.3 additions are additive, not replacement. Each tutorial's fix prompt was framed to respect this boundary.

- **Deprecation notes need both the deprecated form and the migration form.** The F-004 YAML example in Tutorial 2 used `op: append_evidence` — simply marking it "deprecated" without showing the v0.0.3 equivalent (`op: append, target: "evidence_bank"`) would leave readers stuck. The audit prompt captures both.

- **`DanglingRefError` resolution pattern is non-obvious and must be explicit.** The error class name alone doesn't tell the user what to do. The fix prompt specifies: clear referencing sections first via `set` patches, then retry the `delete`. This level of specificity is what makes the audit useful vs. a bare "update for v0.0.3" instruction.
