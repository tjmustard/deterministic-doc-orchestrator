## Approach & Methodology

This was a HACF **Phase 1 (Specification)** session, using the `/hyper-architect` skill as a structured one-question-at-a-time interview. The Architect read the existing codebase, v0.0.1 SuperPRD, and four PRD stubs before asking a single question — pre-computing recommended answers from first principles + existing patterns to let the designer move fast by accepting or correcting, rather than starting from a blank canvas. Decisions were resolved depth-first: scope before data boundary, mutation safety before storage layout, storage before blast radius, before personas/permissions, before testing strategy. The five HACF phases ran sequentially (Core Mutation → Data/Blast Radius → Personas/Permissions → Novel Frontier → Draft Generation).

## Key Decisions & Rationale

| Decision | Alternatives Considered | Reason Chosen |
|---|---|---|
| Defer `ddo-run` composite to v0.0.3 | Ship `ddo-run` in v0.0.2 as a 5-phase chain | Auto-chaining a single context across all phases defeats the fresh-context firewall and HITL gates — the contamination invariant is load-bearing, not cosmetic |
| `ddo.refine` mutates the parsed dict (never YAML text) | Agent hand-edits YAML text; skill calls `ruamel.yaml` for structure-preserving edits | Text-level edits can corrupt structure; dict-level + in-memory `validate()` before write makes the corruption surface formally zero (gate catches it before any I/O) |
| Report/log contracts in `ddo.review` (not `ddo/schemas/`) | Add `red_team_report.yaml` and `interview_log.yaml` to `ddo/schemas/` | `ddo/schemas/` holds author-facing document-type contracts; the report/log are pipeline-internal control state — mixing them would blur the module boundary |
| Full `review_history/` with `_vN` files in v0.0.2 | Keep lean (working files only, `meta.review_log` for traceability) | Designer explicitly chose full auditability; `_vN` derived in code prevents hand-curation errors |
| `history.yaml` (machine) + derived `history.md` (human) | Single markdown summary only | Consistent with the data/view duality pattern established in v0.0.1 — the machine source is canonical; the human view is always code-generated |
| Fresh-context firewall only at `ddo-red-team` | Fresh context at every phase boundary | `ddo-interview` and `ddo-refine` are collaborative (resolving findings *with* the human); the report YAML is the clean hand-off; forcing a new context per phase would break the session flow |
| Structural validation of critique only (no quality scoring) | Add an LLM-judge or rubric-based quality scorer | Quality scoring is itself non-deterministic; deferring keeps the deterministic/novel boundary clean and avoids scoring theater |
| US-005 "safety linchpin" as a named unit test | Trust `validate()` indirectly via integration tests | The linchpin is the single test that proves the system's core promise ("patch a gap without corrupting the YAML"); it deserves a dedicated, named, deterministic assertion |
| Confidence score 8/10 (not higher) | Score 9/10 | Five open questions (patch-grammar expressiveness, diff presentation safety, partial refinement, `_vN` robustness, interview→report update atomicity) are real design questions for the Red Team — scoring lower honestly flags where the RT should focus |

## Patterns & Lessons

- **Pre-compute recommendations, don't blank-slate interview.** Reading the codebase, v0.0.1 SuperPRD, and all four skill stubs before asking the first question let every question arrive with a concrete recommended answer. The designer could accept ("agreed as written") and move fast, or correct the framing — far more efficient than open-ended elicitation.
- **Highest-risk path first (depth-first).** `ddo.refine`'s mutation of the sacred YAML was the single riskiest operation. Resolving the mutation safety model in Phase 2a (before storage layout, before firewall placement) meant every downstream decision was already bounded by the safety contract.
- **The "Iterative state" check changes everything.** In a greenfield session the Architect asks "what problem does this solve?" In an Iterative session with a populated `architecture.yml`, the Architect derives the blast-radius hypothesis and presents it as a recommendation — the designer confirms or corrects, saving multiple rounds of exploratory questioning.
- **Surfacing open questions with confidence <9 is more honest than papering over them.** Five real design questions (patch-grammar expressiveness, diff safety, partial refinement, `_vN` robustness, interview→report atomicity) were flagged in §2 at confidence 8/10. This gives the Red Team a focused attack surface and avoids the false comfort of a 9/10 that papers over implementation uncertainty.
- **The data/view duality pattern generalises.** v0.0.1 established: machine-readable YAML is canonical; Markdown views are code-generated, read-only, and never parsed back. v0.0.2 applies this pattern to three new pairs: report YAML + view MD, interview log YAML, and history YAML + history MD. Recognizing the pattern early made the storage layout decisions fast and consistent.
