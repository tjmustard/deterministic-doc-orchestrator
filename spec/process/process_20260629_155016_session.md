## Key Decisions & Rationale

| Decision | Alternatives Considered | Reason Chosen |
|---|---|---|
| Both constrained `set` AND `refine_structural_check` in new code | Only `set` constraint; only structural check; defer both to v0.0.3 | Constrained `set` alone doesn't catch section deletion; structural check alone doesn't stop type-changing `set`; `validation_gate` must not be modified (D5 blast-radius) |
| Pre-refine snapshot as `document_data_pre_vN.yaml` | Snapshot in `Documents/` root; git-based rollback | Snapshot in `review_history/` keeps all review artifacts collocated; git rollback doesn't work because `Documents/` is gitignored |
| `safe_dump(sort_keys=False)` with no ruamel | ruamel.yaml for comment preservation | Adding a new runtime dep for comment preservation (which only affects readability) failed the cost/benefit test; snapshot preserves the original |
| Hand-rolled minimal path DSL, never `eval` | Existing library (jsonpath, dacite); richer DSL with structural ops | Security-critical path; library dependency; structural ops defer to v0.0.3 |
| Split `decision_recorded` / `applied` flags | Single `resolved` flag; mark applied at interview time | Truthfulness: interview doesn't know if the patch will succeed; `applied` must only be set after `commit_refine` + re-render both succeed |
| `detect_incomplete_pass` on entry, file tree authoritative | Skip detection; trust `history.yaml` | If a prior pass was half-written, stacking a new `_vN` would create phantom history; file tree is observable truth, `history.yaml` is derived |
| New `SuperPRD_v0.0.2_AdversarialLoop.md` file | Overwrite `SuperPRD.md` | v0.0.1 `SuperPRD.md` is the current `ddo_system.associated_file` binding in `architecture.yml`; clobbering it would break the v0.0.1 audit trail |
| `review_history/` path builder lives in `ddo.review` | Add to `path_deriver` | D5: `path_deriver` is a v0.0.1 atomic node, reused not modified |

## Patterns & Lessons

- **Verify Red Team claims in code before framing decisions.** The RT report asserted `validate()` was "insufficient" — a vague claim until confirmed by reading `validation.py`. Doing this before showing the author any options converted a contested point into a clear, agreed fact, making the subsequent trade-off question much simpler.
- **The sentinel mismatch was a doc bug, not an architecture gap.** Always grep both the code and the docs before concluding a sentinel-form inconsistency is an architecture problem. Here `CLAUDE.md` was stale; the code (`validation.py`) and the skill (`ddo-ingest.md`) were correct and consistent.
- **`python` vs `python3` on Ubuntu/Debian.** The archive script's shebang and the HACF convention use `python`, but the system may not have a `python` symlink. Use `python3` explicitly or update the call.
- **D5 blast-radius principle as a decision accelerant.** Once `validation_gate`, `path_deriver`, `ingest_helpers`, and `build_orchestrator` are declared "reused, not modified," many design questions collapse: any guard that would have modified those nodes instead becomes a new code location (e.g., `refine_structural_check` in `ddo.refine`, `review_history/` builder in `ddo.review`).
- **SuperPRD versioning:** When a new SuperPRD doesn't replace but extends an existing one, write a new file to preserve the old audit trail. Update `architecture.yml`'s `associated_file` binding via `/hyper-audit` after code lands — don't clobber it during spec.
